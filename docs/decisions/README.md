# 스도쿠 설계 결정 목록과 ID 기록

현재 구조는 [architecture.md](../../architecture.md), 작업별 목표와 진행은 [작업 목록](../../tasks/README.md)에서 관리한다.
공통 기준은 [AGENTS.md](../../AGENTS.md)다. 작업 ID와 결정 ID는 별개다.

## 새 기록 생성

1. 관련 기존 결정을 먼저 읽고 새 결정이 필요한지 판단한다.
2. 하위·보관 파일, 제목 ID와 이 목록의 예약·사용 ID를 확인한다. 프로젝트 규칙이 없으면 숫자 최댓값 다음 번호를 사용하며 기록이 없으면 001부터 시작한다. 숫자는 최소 세 자리다.
3. 제안·채택됨·기각됨·대체됨·보관·삭제 기록의 ID는 재사용하지 않는다. 파일과 목록의 차이는 확인한다. 과거 이력이 없으면 확인 가능한 범위와 미확인 범위를 기록한다.
4. [decision-template.md](decision-template.md)를 복사해 `<결정ID>-<결정명>.md`를 만든다. 원본이 없으면 배경·대안·결정·이유·영향·상태·관련 링크를 포함한다.
5. 생성 직전 ID와 경로 중복을 확인하고 기존 파일을 덮어쓰지 않는 방식으로 생성한다. 같은 ID의 다른 파일명도 충돌이다. 새 생성 충돌은 새 ID로 해결하고 기존 중복 기록은 보고한다.
6. 파일명, 제목, 목록과 관련 작업 링크를 맞춘다. 예: `007-session-expiry.md`의 제목은 `D-007: 세션 만료 정책`이다.

## 상태와 구현 시점

- 제안 → 채택됨 또는 기각됨: 결정 권한이 확인된 사용자 승인·팀 규칙이나 팀 리뷰를 근거로 상태와 결정일을 기록한다. 이미 확인된 승인을 다시 요청하지 않는다.
- 채택됨은 구현 완료가 아니다. architecture.md는 실제 반영된 구조와 결정만 연결한다. 예정된 전환은 관련 작업에서 관리한다.
- 기존 결정을 바꾸면 새 ID로 제안한다. 실제 전환 전에는 기존 결정 상태를 채택됨으로 유지한다. 전환 후 기존 기록을 대체됨으로 바꾸고 양방향 링크·목록을 갱신한다.
- 단계적 전환이면 각 결정의 적용 범위와 전환 현황을 적는다. 과거 이유는 보존한다.
- 상태는 제안 / 채택됨 / 기각됨 / 대체됨이다. 파일의 보관·삭제 여부와 구분한다.

## 보존과 동시 작업

- 삭제·이동 후에도 목록에 ID와 상태, 설명·이동 위치를 남겨 재사용을 막는다. 확인 불가능한 과거 이유·날짜·참여자를 채우지 않는다.
- 팀 공용 발급 규칙을 우선한다. 로컬 최댓값 확인은 다른 브랜치의 발급을 보장하지 않는다.
- 작업용 Issue 번호를 결정 ID로 자동 복사하지 않는다. 하나의 작업에 여러 결정이 있을 수 있다.
- 병합 시 ID 충돌을 해결하면 제목·목록·작업·아키텍처 링크도 함께 정리한다.
- 작은 구현 선택은 작업 문서에 기록해도 된다. 원본 템플릿에는 실제 결정 내용을 작성하지 않는다.
