## 배경과 제약

DOM을 게임 데이터의 원본으로 삼으면 입력·단서·완료 조건과 타이머를 재현 가능하게 검증하기 어렵다.
렌더링과 사용자의 입력이 같은 원본 상태를 기준으로 동작하고 이전 비동기 요청이 새 게임을 덮어쓰지 않아야 한다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 명시적 상태 + 순수 reducer + 효과 조정 | 단위 검증과 흐름 추적, 변경 책임 분리 | 상태·이벤트·효과 코드를 나눠 작성해야 함 |
| DOM 값을 직접 읽고 변경 | 초기 구현이 짧음 | 상태·단서·완료와 테스트가 DOM에 결합 |
| 외부 상태 관리 라이브러리 | 도구 제공 | 외부 의존성 없음 범위를 벗어남 |

## 결정과 이유

사용자 이벤트 → Action → 상태 갱신 → Render 흐름을 사용하며 renderer는 상태를 변경하지 않는다.
초기 puzzle과 현재 values를 분리하고 메모는 셀별 독립 Set으로 관리한다.
오류는 행·열·박스 충돌만 표시하고 해답과 비교하지 않는다. 완료는 빈칸 없음·유효성·단서 일치를 모두 요구한다.
메모는 빈 편집 셀에만 적용하고 실제 값 입력 시 그 셀의 메모를 지운다.

idle·generating·playing·completed·error 상태, 증가하는 requestId, AbortController로 요청을 분리한다.
난이도 선택은 다음 게임에 적용하고 현재 퍼즐은 새 게임을 누를 때만 바꾼다.
타이머는 퍼즐 준비 후 시작해 경과 시각 차이로 계산하며 숨겨진 탭 시간도 포함한다.
새 게임은 초기화, 완료는 정지, 일시정지·새로고침 저장·OS 절전 간 보존은 범위 밖이다.

## 영향과 후속 조치

시계·난수·Promise 효과·DOM은 reducer 밖에 둔다. 요청·타이머·이벤트 정리 책임은 main에 있다.
키보드·터치·숫자 패드·포커스와 완료 dialog는 실제 브라우저로 확인해야 한다.
보드의 상태 전이는 Node 테스트로 검증하고 콘솔 함수 결과로 UI 통과를 대신하지 않는다.

## 재검토 조건

저장·복구, 실행 취소, 일시정지, 정답 기반 힌트, 여러 게임 세션 등 새로운 상태 요구가 생길 때 재검토한다.
