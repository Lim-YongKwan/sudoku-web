## 배경과 제약

완성 보드에서 숫자만 무작위로 제거하면 해답 수를 보장하지 못한다.
유일해를 유지하면서도 탐색이 무한정 지속되거나 브라우저 입력을 장시간 막지 않도록 종료·양보 기준이 필요하다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 제거 후 해답 수 검사 + 제한·협력적 양보 | 요구사항 충족, 동일 core를 Node·브라우저에서 검증 가능 | 생성 실패와 비동기·취소 처리가 필요 |
| 유일해 검사 없이 단순 제거 | 구현과 생성이 빠름 | 퍼즐 요구사항 불충족 |
| 처음부터 Web Worker | 메인 스레드 분리 | MVP에 추가 메시지·워커 생명주기·테스트 복잡도 |
| 미리 저장한 퍼즐만 제공 | 실행 중 생성 부담 없음 | 새 퍼즐 생성 알고리즘 학습 요구와 다름 |

## 결정과 이유

해답 개수를 최대 2개까지 찾고 전체 탐색 완료/count=1인 경우에만 제거를 유지한다.
중단·예산 초과 상태에서 발견한 1개를 유일해로 해석하지 않는다.
빈칸 목표는 쉬움 35·보통 45·어려움 50이며 간이 난이도로 표현한다.
목표에 도달하지 못하면 제한 내 재시도 후 실패하고 조용히 다른 목표를 반환하지 않는다.

초기값은 시도 8회, 전체 1,000,000노드·5,000ms, 개별 탐색 100,000노드·2,000ms,
128노드마다 취소·시간 검사와 task 양보다. 제거 사이에도 검사한다. 생성 전체의 남은 예산을 공유한다.
노드는 DFS 상태 진입 수로 센다. 시간 초과는 검사 간격만큼 초과할 수 있다.
난수·시계·양보 함수를 주입하고 Promise 기반 엔진에서 DOM 없이 같은 계약을 검증한다.
현재 선택은 협력적 양보이며 반응성 측정이 불충분하면 Web Worker를 재검토한다.

## 영향과 후속 조치

UI에 생성 중 잠금·실패·재시도가 필요하다. 새 요청은 이전 생성을 취소하고 오래된 결과를 무시해야 한다.
초기 예산을 유지한 002 측정에서 세 난이도 각 3개 seed가 성공했다. 측정 환경·통계는 002 구현 기록을 따른다. 모든 기기의 성능이나 실제 UI 반응성을 보장하는 결과는 아니며 조정 시 실제 근거를 남긴다.
유일해·목표 빈칸을 완화하는 변경은 성능 조정과 구분한다. 난이도별 성공 fixture와 실패 경로를 실제 테스트해야 한다.

## 재검토 조건

기본 예산에서 어떤 난이도도 성공하지 못하거나 브라우저 반응성이 요구를 충족하지 못할 때,
논리 풀이 난이도·퍼즐 저장·워커 도입 요구가 생길 때 재검토한다.
