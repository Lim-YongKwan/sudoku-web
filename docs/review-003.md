## 관련 범위 리뷰

- 입력·상태: Board·메모·선택 인덱스 형식을 확인하고 puzzle/values와 notes의 원본을 읽기만 한다. 렌더러는 이벤트·난수·상태 갱신을 소유하지 않는다.
- DOM: WeakMap으로 81개 셀과 내부 노드를 재사용한다. textContent·class·접근성 속성을 갱신하며 innerHTML로 사용자 값을 해석하지 않는다. 노드·포커스 보존의 실제 관찰은 아직 남았다.
- 이름·시각: 행·열·단서/입력·값·메모·충돌을 이름으로 전달한다. 오류는 값 충돌이며 정답 비교가 없다. 포커스 outline·3x3 경계·단서 구분·반응형 CSS를 검토했지만 시각 통과로 판정하지 않았다.
- 초기 연결: 실제 generatePuzzle(easy)의 success만 렌더링하고 난이도·35개 빈칸·형식·논리 유효성을 확인한다. 실패는 빈 비활성 보드·일반 안내이며 가짜 퍼즐이 없다.
- 비동기·정리: 초기화 signal 확인과 예외 안내, pagehide 취소·캐시 복귀 재개를 검토했다. 반복 새 게임·requestId 효과·store는 004·005 범위다.
- 개발 fixture: 앱과 분리해 고정 보드·실패 주입·노드/포커스·상태 불변을 검사한다. 새 board-assertions.js는 측정 해석용 순수 함수이며 UI 검사 자체를 대신하지 않는다.
- 범위·의존성: 외부 패키지·번들러를 추가하지 않았다. core·utils의 DOM/Node 전용 import가 없고 앱에서 fixture를 import하지 않는다.

## 당시 해제 조건·수동 절차

[03 기록의 사용자 실행 절차](board-003.md)를 따른다. Node 22 이상으로 npm start 후 앱과 /tests/browser/board.html을 연다.

1. 앱의 실제 easy 퍼즐 81셀·46단서·35빈칸과 준비 완료 안내·Console 오류 부재를 확인한다.
2. 실제 viewport 320×800·1280×900 각각에서 검증 페이지의 “포커스·재렌더 검사”를 실행한다. 새 출력은 facts와 checks로 나뉜다.
3. checks의 cells81·sameNodes·focusPreserved·stateUnchanged·clueLabel·blankNotesLabel·oneTabStop·noHorizontalOverflow·squareCell·boxRightThick·boxBottomThick이 모두 true인지 기록한다.
4. facts의 실제 viewport·양의 셀 크기·경계3px과 보드의 시각 형태·가로 넘침 부재를 확인한다. Tab 포커스의 outline과 접근성 이름을 직접 확인한다.
5. 실패 주입 PASS·빈 비활성 보드·안내, 복원 동작과 Console/Network를 확인한다. 복원은 과거 합격 표식을 지우는 것이 정상이다.
6. 가능하면 생성 중 다른 페이지로 이동 후 뒤로 돌아오는 캐시 복귀도 확인한다. pageshow.persisted가 관찰되지 않은 환경에서는 해당 검사를 미실행으로 적고 일반 복귀 결과와 구분한다.
7. 브라우저 이름·버전·viewport·기대/실제 결과를 기록하고 서버를 Ctrl+C로 종료한다.
8. 새 증거를 바탕으로 같은 003의 완료 조건·목록을 재평가한다. 필수 조건을 후속 작업으로 넘겨 완료 처리하지 않는다.

현재는 05 준비 또는 004의 선행 완료로 취급하지 않는다. 추가 자동 실패는 없지만 실제 UI 검증이 남아 003을 완료로 변경하지 않았다.
